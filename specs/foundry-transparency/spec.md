# Foundry execution transparency

## User scenarios

### US1 — Honest execution status (P1)
As a customer, I can distinguish an Azure AI Foundry response, a deterministic banking response, and a cloud fallback.

### US2 — Safe fallback (P1)
As a customer, when Foundry is unavailable, I receive a clear limitation message and never a response presented as generated by AI.

### US3 — Operational diagnosis (P1)
As an operator, the API response contains an explicit execution mode that can be tested without exposing credentials or internal errors.

## Functional requirements

- **FR-001** Every assistant response MUST include `execution_mode`.
- **FR-002** `execution_mode` MUST be one of `azure-foundry`, `deterministic`, or `cloud-fallback`.
- **FR-003** Cloud Foundry communication failures MUST return `cloud-fallback` and a limitation message.
- **FR-004** Deterministic banking routes MUST return `deterministic`.
- **FR-005** A successful model round MUST return `azure-foundry`.
- **FR-006** The frontend MUST render the execution mode beside assistant messages.
- **FR-007** Tests MUST cover each mode and preserve customer isolation.

## Success criteria

- A Foundry failure is observable as `cloud-fallback`, never as an unlabeled answer.
- Structured balance/loan/request responses are labeled `deterministic`.
- A successful model response is labeled `azure-foundry`.
- OpenAPI, backend tests, frontend typecheck, and build pass.

## Out of scope

Changing Azure quota, bypassing Foundry failures, or presenting deterministic data as LLM output.
